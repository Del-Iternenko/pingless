# Как устроен OpenLag

## Узлы

- **Клиент** на Windows. Перехватывает UDP выбранных процессов и отправляет его в туннель.
- **Exit**: relay рядом с игровыми серверами. Расшифровывает трафик и общается с игрой.
  Игровой сервер видит IP exit, поэтому **все маршруты одного потока сходятся в один
  exit**. Поток привязывается к exit при создании и больше не переезжает.
- **Bridge**: промежуточный relay. Не расшифровывает трафик, пересылает только своему
  exit. Нужен, чтобы получить к одному exit разные сетевые маршруты.
- **Маршрут**: способ дойти до exit: напрямую, через bridge, через другой порт exit или
  через другой сетевой интерфейс (`bind`).

## Протокол (`openlag-proto`)

Каждая датаграмма: 18-байтный открытый заголовок (версия, тип, id сессии, счётчик) и
тело, зашифрованное ChaCha20-Poly1305. Заголовок аутентифицирован как AAD.

- Ключ сессии = BLAKE3(мастер-ключ из PSK, id сессии). У каждого exit своя сессия.
- Nonce = счётчик. У клиента старший бит 0, у relay 1, оба стартуют со случайного
  смещения. Поэтому перезапуск relay не повторяет nonce, а отражённый пакет не
  принимается.
- `Data` несёт `flow`, `seq` и адрес игрового сервера в **каждом** пакете. Relay не
  нужно отдельное сообщение «открыть поток», которое могло бы потеряться.
- `Ping`/`Pong` для замера маршрута. RTT считается по собственному времени отправки,
  поэтому подделанный Pong не может показать низкий пинг.
- `Close` освобождает поток на exit сразу, без ожидания таймаута.

## Multipath и дубли

Пакет шифруется один раз и уходит одинаковыми байтами по N лучшим маршрутам. Обе
стороны пропускают через окно последовательностей (`SeqWindow`, 1024 номера) только
первую копию. Exit отправляет ответ по всем живым путям клиента, которые были
активны за последние 5 секунд.

UDP не упорядочивается и не переотправляется: для игры поздний пакет бесполезен.
Пакеты старше окна отбрасываются.

## Выбор маршрута (`openlag-core`)

- Ping на каждом маршруте каждые 250 мс. Сглаженный RTT и джиттер считаются как в
  RFC 6298, потери — по последним 50 пробам (таймаут 2 с).
- Оценка = srtt + 2·jitter + 10 мс за каждый процент потерь.
- Маршрут считается мёртвым, если 3 с нет ответа.
- Активный набор — до `multipath` лучших маршрутов. Новый маршрут заменяет худший
  активный, только если лучше на `switch_margin_ms`, чтобы выбор не «прыгал».
- Новый поток идёт в exit с лучшим маршрутом. Если не отвечает ни один relay, поток
  помечается **direct**: пакеты идут без туннеля и игра работает как без OpenLag.
  Позже такой поток в туннель не переводится, потому что смена IP рвёт сессию.

## Перехват (`openlag-capture`)

- WinDivert, слой NETWORK, фильтр `outbound and udp and !loopback`.
- Владелец порта берётся из событий слоя SOCKET (bind/connect/close) с PID процесса.
  Запасной путь — `GetExtendedUdpTable`, потому что первый пакет игры может прийти
  раньше события bind.
- Не трогаем: локальные сети, loopback, мультикаст, CGNAT 100.64/10, собственный
  процесс.
- Ответ от relay собирается в IP+UDP-пакет **от адреса игрового сервера** к сокету
  игры и инжектится как входящий на тот же интерфейс. Кортеж совпадает с
  исходящим потоком игры, поэтому Windows Firewall принимает его как ответ.
- Контрольные суммы IPv4/UDP/IPv6 считаются в коде и проверяются в тестах.
- Сокеты, открытые до запуска, остаются direct (`tunnel_existing`), пока игра их не
  закроет.
- На слое WFP исходящие датаграммы приходят целыми, ещё до IP-фрагментации, так что
  собирать фрагменты не нужно (в отличие от фильтров уровня NDIS).

## Защита relay

- Exit не отправляет трафик в приватные, loopback и link-local адреса без
  `--allow-private`.
- Новая сессия регистрируется только после успешной расшифровки пакета, так что
  мусор не заполняет таблицу.
- Лимиты: 4096 сессий, 256 потоков на сессию, 8192 записей на bridge. Простаивающие
  потоки закрываются через 120 с.
- Bridge пересылает только своему exit и принимает ответы только от него.
- Ошибка ICMP unreachable (`ConnectionReset` на Windows) не останавливает цикл приёма.

## Известные ограничения

- TCP не туннелируется: TCP-соединения игр идут напрямую.
- Накладные расходы около 53 байт на пакет. Датаграмма игры больше ~1400 байт будет
  фрагментирована на пути к relay.
- Защиты от повтора старых пакетов в рамках сессии нет, кроме окна потока.
- Привязка маршрута к интерфейсу пока делается через `bind` на адрес. Нужно добавить
  `IP_UNICAST_IF`, чтобы Windows точно не увела трафик в другой интерфейс.

## Тесты

`cargo test --workspace` поднимает на loopback эхо-«игру», exit, bridge и каналы с
потерями:
- два маршрута с потерей 30% в каждую сторону дают заметно больше доставленных
  пакетов, чем один, и ни один пакет не доставляется дважды;
- при остановке активного bridge трафик переходит на второй маршрут;
- без живых relay поток уходит direct и остаётся direct;
- клиент с чужим ключом не проходит через exit.
